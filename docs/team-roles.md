# CookKG 小组成员分工

> 文档状态：小组讨论稿 v0.1
>
> 小组规模：3 人
>
> 当前课题：基于食材层级知识图谱与约束优化的可解释家庭菜单规划系统

## 1. 分工原则

小组按照三个可以独立验收、最终通过接口集成的方向分工：

1. 项目统筹、UI 与系统集成；
2. 数据标注、食材本体与图谱构建；
3. 约束推理、推荐算法与后端接口。

每位成员都应拥有可以独立讲解的代码、数据或页面成果。模块负责人对本模块的设计、实现、测试、文档和答辩说明负责。

| --- | --- | --- |

| `Zouyilin06` | 数据与知识图谱负责人 | 菜谱解析审核、食材归一化、食材层级、本体设计、NetworkX/Neo4j 图谱与数据质量 |
| `98K12WQ` | 算法与后端负责人 | 忌口图推理、候选过滤、联合补购优化、后端 API、算法测试与评测脚本 |

## 3. 组长（你）：总体协调、UI 与系统集成

### 3.1 主要职责

- 确定问题定义、项目范围和阶段目标；
- 维护总体架构和模块接口；
- 设计并实现中文 Web UI；
- 完成库存、常备调料、忌口、菜数和补购上限的输入交互；
- 展示推荐菜单、补购清单、库存利用、排除原因和来源证据；
- 设计局部知识图谱可视化；
- 集成数据模块、算法模块和后端接口；
- 组织代码审查、阶段验收和演示排练；
- 统筹项目说明、实验报告、答辩 PPT 和演示脚本。

### 3.2 主要交付物

- 项目需求与总体架构文档；
- UI 原型和中文 Web 页面；
- 菜单推荐结果页与图谱解释页；
- 前后端联调版本；
- 项目 README、演示脚本和答辩材料；
- 最终验收清单与实验结论。

### 3.3 UI 首版页面

1. **条件输入：**已有食材、常备调料、排除食材、菜数和最多补购数；
2. **菜单结果：**菜谱卡片、库存覆盖和合并补购清单；
3. **约束解释：**展示“菜谱 -> 食材 -> 食材类别”的保留或淘汰路径；
4. **菜谱详情：**用量、操作步骤和固定版本原文链接。

### 3.4 验收标准

- 用户可以完成一次完整菜单推荐；
- 输入校验和无解提示清晰；
- 页面不复制后端推荐逻辑；
- 每个结果能够打开来源并查看解释；
- 桌面浏览器下完成演示流程，无阻断性错误。

## 4. Zouyilin06：数据与知识图谱

### 4.1 主要职责

- 维护固定版本 HowToCook 数据源；
- 完善 Markdown 解析规则和质量报告；
- 根据标注规范审核不少于分配数量的菜谱；
- 拆分并列食材、可选项和食材选择组；
- 建立可审阅的食材标准名称与别名字典；
- 建立食材类别和上下位关系；
- 标注经过确认的复合食材成分关系；
- 维护菜谱、食材、类别和工具的图谱模式；
- 生成标准 JSONL、NetworkX 图和 Neo4j 导入数据；
- 编写图谱一致性、幂等导入和代表性查询测试。

### 4.2 主要交付物

- 100 道人工审核菜谱数据；
- 食材别名字典和食材分类层级表；
- 标注记录和数据质量报告；
- 标准 `recipes.jsonl` 数据；
- NetworkX 图谱文件；
- Neo4j 导入和验证命令；
- 典型 Cypher 查询与图谱截图。

### 4.3 数据接口责任

数据模块向算法模块提供稳定的数据对象：

```json
{
  "id": "dishes/example.md",
  "name": "示例菜",
  "review_state": "confirmed",
  "ingredients": [
    {
      "id": "小米椒",
      "requirement": "required",
      "review_state": "confirmed",
      "group_id": null,
      "quantity_raw": ["小米椒 4 颗"],
      "evidence": ["dishes/example.md:20"]
    }
  ]
}
```

同时提供食材层级关系：

```json
{"child": "小米椒", "parent": "辣椒", "review_state": "confirmed"}
```

字段变更必须先更新数据模型和接口文档，再通知其他成员联调。

### 4.4 验收标准

- 审核记录与源文件哈希绑定；
- 不存在未拆分的并列食材；
- 工具不会进入补购食材；
- 必需、可选和选择组均有证据；
- 食材标准名没有无依据的合并；
- 严格推荐数据中不存在 `pending` 关系；
- 重复构建得到稳定 ID 和一致图谱；
- 重复导入 Neo4j 不产生重复节点或关系。

## 5. 98K12WQ：算法与后端

### 5.1 主要职责

- 统一处理已有食材、常备调料和排除条件；
- 根据别名和食材层级扩展排除集合；

- 计算多道菜必需食材并集和补购集合；
- 实现稳定排序、候选池限制和无解说明；
- 提供供 UI 调用的 FastAPI 接口；
- 编写算法单元测试、端到端测试和对照实验脚本；
- 输出忌口推理路径和推荐解释对象。

### 5.2 主要交付物

- 忌口扩展与图谱推理模块；
- 菜谱硬约束过滤模块；
- 联合补购优化模块；
- FastAPI 服务和 OpenAPI 文档；
- 推荐结果与解释的 JSON 接口；
- 独立穷举对照测试；
- 关键词匹配与图谱推理对照实验；
- 逐道选菜与联合优化对照实验。

### 5.3 后端接口责任

推荐请求建议为：

```json
{
  "have": ["鸡蛋", "土豆"],
  "pantry": ["盐", "食用油"],
  "exclude": ["辣椒"],
  "count": 2,
  "max_buy": 3,
  "limit": 5
}
```

响应至少包含：

```json
{
  "plans": [],
  "reason": null,
  "candidate_count": 0,
  "normalized_input": {},
  "excluded_ingredients": [],
  "explanations": []
}
```

后端负责保证硬约束正确，UI 只负责收集输入和展示结果。

### 5.4 验收标准

- 共享缺料在同一菜单中只计算一次；
- 必需食材命中排除集合时菜谱被淘汰；
- 可选食材命中排除集合时菜谱保留并省略该项；
- 上位类别排除能够命中审核后的下位食材；
- 用户未声明时不默认拥有油盐等调料；
- 无可行组合时不自动放宽条件；
- 相同输入和数据版本产生相同排序；
- API 输出符合约定的数据模型。

## 8. Git 协作约定

- `main` 始终保持可运行；
- 使用短生命周期功能分支；
- 建议分支前缀：`ui/`、`data/`、`graph/`、`algorithm/`、`api/`、`docs/`；
- 一次 Pull Request 只解决一个明确问题；
- Pull Request 写清问题、修改结果和验证方式；
- 数据模型或 API 变更需要三人知晓；
- 不提交原始 HowToCook 数据、生成图谱、密码或 API Key；
- 合并前运行对应测试和 Ruff 检查。

## 9. 模块边界

- UI 不复制推荐规则，以后端返回结果为准；
- 算法模块不直接解析 Markdown，只读取标准数据；
- 数据模块不决定菜单排序，只保证图谱数据正确；
- Neo4j 与 NetworkX 使用同一份标准数据；
- 问题范围、公共模型和接口变更由组长组织确认；
- 模块负责人修复本模块缺陷，接口两侧共同处理联调问题。
