# Zouyilin06 答辩与演示脚本

## 90 秒讲解

“我负责 CookKG 的数据标注与知识图谱模块。原始数据来自固定提交的 HowToCook，菜谱用相对路径
作为稳定 ID，每条标注都绑定源文件哈希、行号和逐字引文。这样上游文本一旦变化，旧审核就会
自动失效。

数据模型把食材需求分成必需、可选、选择组和未知，并把审核状态单独保存。工具不会进入购物
清单，水是家庭资源，油盐仍由用户决定是否已有。用量保留精确量、范围、公式和无法安全解析的
上下文；例如葱姜蒜共15克只记录为组合总量，不会错误地给每项15克。

同一份标准数据生成 NetworkX 与 Neo4j 图。当前草稿图包含 539 个节点和1,292条关系。
我用重复构建、重复导入、全部属性回读和六个代表性查询验证一致性，78项测试全部通过。
当前数据仍是100道AI辅助草稿，39道含需人工裁决的问题，所以我不会把它说成100道人工审核，
也不会编造准确率。课程要求的双人标注、人工签名、交叉复核和接口确认仍需小组实际完成。”

## 演示顺序

1. 打开 `review-100.html`，展示原文与标注并排、证据行跳转、未预选审核框。
2. 搜索“小炒肉”，解释 `小炒肉 -> 小米椒 -> 辣椒类`，说明类别排除如何获得依据。
3. 打开 `neo4j-hierarchy.png` 或运行 `representative-queries.cypher` 中的辣椒查询。
4. 展示“芥末黄油罗氏虾”的三种酒为选择组，而不是三项都必须购买。
5. 打开 `issue-resolution-queue.json`，说明源文矛盾如何保留并阻止严格推荐。
6. 打开 `validation-results.json`，展示重复构建、Neo4j 回读、查询对照和测试结果。

## 常见提问

**为什么需要知识图谱？** 纯字符串排除“辣椒”无法可靠命中“小米椒”。IS_A 与 SUBCLASS_OF
提供可追溯路径，必需、可选和选择关系又决定淘汰、省略或组内选择。

**数据准确率是多少？** 当前没有独立裁决后的人工金标准，不能给百分比。已经验证的是来源绑定、
结构一致性和数据库往返正确性；语义准确率必须在人工审核后计算。

**为什么有 pending？** 原菜谱存在数量冲突、遗漏步骤和开放替代。证据不足时保留问题比猜测更可靠，
严格推荐门禁会排除这些菜谱。

**如何避免重复导入？** 每个节点和关系使用源版本、接口版本与稳定业务 ID 生成键；同一快照在事务中
整体替换并逐项回读验证，因此重复运行结果一致。
