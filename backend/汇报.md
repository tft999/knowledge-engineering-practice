## 一、项目定位与本模块的职责边界

本模块实现 CookKG 的**「语义过滤 + 组合优化」技术闭环**，是整个系统唯一负责「决定菜单是否满足硬约束」的部分。

按照 `team-roles.md` 的模块边界约定，本模块严格做到：

1. **不解析 Markdown**：只读取数据模块（`Zouyilin06`）产出的标准数据（`recipes.jsonl` / `taxonomy.jsonl` / `aliases.json`）。
2. **不复制 UI 逻辑**：前端只调用 FastAPI 接口并展示结果，推荐规则全部在后端。
3. **硬约束判断不依赖大模型**：所有推理是确定性的图遍历与集合运算。

整个推荐流程分两个确定性阶段（与 `PROJECT.md` 第 2.1 节一致）：

```
用户输入 → 输入归一化 → 忌口推理(排除集合扩展) → 候选硬约束过滤 → 联合补购优化 → 响应
```

  normalization.py     taxonomy.py      exclusion.py       filter.py     recommend.py
  （别名→标准名）     （层级有向图）    （排除集合扩展）   （硬约束过滤）  （联合补购优化）
                                            │
                                            ▼
                              models.py（贯穿全程的数据契约）
                                            │
                        ┌───────────────────┴────────────────────┐

### （二）核心包 `cookkg/`

#### 4. `cookkg/__init__.py` —— 包入口

- 模块 docstring 复述了模块边界（不解析 Markdown、UI 不复制推荐规则）。
- 通过 `from .xxx import ...` 把常用符号（`RecommendationEngine`、数据模型、加载函数）提升到包顶层，外部可 `from cookkg import RecommendationEngine` 直接使用。
- 声明 `__version__ = "0.2.0"`，与 `pyproject.toml` 对齐。
- `__all__` 明确导出清单。

#### 5. `cookkg/errors.py` —— 自定义异常

定义三层异常，用于给上层清晰的失败信号：

```python
CookKGError            # 基础异常
├── DataLoadError      # 标准数据缺失/格式错误（loader 抛出）
└── InvalidInputError  # 用户输入非法（预留，Pydantic 校验已覆盖 count 范围）
```

**设计要点**：`InvalidInputError` 目前是预留，因为 `count` 的 1~3 约束已由 Pydantic 的 `ge/le` 在 `RecommendRequest` 层拦截，FastAPI 会返回 422。保留它是为了未来非 API 入口（如直接调用引擎）时能抛出统一语义的异常。

#### 6. `cookkg/models.py` —— 数据模型与接口契约（核心契约文件）

这是**三人联调的契约中枢**，定义两类对象：

**A. 数据模块 → 算法模块** 的标准数据对象：

| 类 | 对应图谱实体 | 关键字段 |
| --- | --- | --- |
| `IngredientUse` | 菜谱-食材关系 | `id`（标准食材名）、`requirement`、`review_state`、`group_id`、`quantity_raw`、`evidence` |
| `ChoiceGroup` | 选择组约束 | `group_id`、`requirement`（required_one_of/optional_one_of）、`min_select`、`max_select`、`open_group` |
| `Recipe` | 菜谱实体 | `id`（相对路径）、`name`、`category`、`difficulty`、`source_url`、`source_hash`、`review_state`、`groups`、`ingredients` |
| `TaxonomyEdge` | 层级边 | `relation`、`child`、`parent`、`review_state` |

**B. 算法模块对外** 的请求响应模型：

| 类 | 作用 |
| --- | --- |
| `RecommendRequest` | 输入：have/pantry/exclude/count/max_buy/limit |
| `NormalizedInput` | 归一化后的输入回显 |
| `Omission` | 被省略的可选食材（含命中排除项、图路径、证据） |
| `Explanation` | 保留/淘汰/省略的解释路径 |
| `PlanRecipe` / `MenuPlan` | 方案中的菜 / 完整方案 |
| `RecommendResponse` | 输出：plans/reason/candidate_count/explanations |

**关键设计决策**：

1. **枚举用 `Literal` 类型**：`Requirement = Literal["required", "optional", "one_of", "unknown"]`，`ReviewState = Literal["auto", "confirmed", "pending", "rejected"]`。这实现了标注规范第 8.1 节「需求语义与审核状态分离」——**不把 `pending` 当成一种使用方式**。
2. **选择组成员不重复存储**：`ChoiceGroup` 只存约束，成员由 `Recipe.ingredients` 中 `requirement == "one_of"` 且 `group_id` 匹配的条目聚合，避免两份数据不一致。
3. **`evidence` 字段贯穿**：菜谱关系、层级边、解释对象都带原文证据位置（如 `dishes/xxx.md:20`），满足「来源可追溯」的创新点。
4. 所有字段用 `Field(description=...)` 标注中文语义，FastAPI 自动生成 OpenAPI 文档时可直接展示。

#### 7. `cookkg/normalization.py` —— 输入归一化

实现 `Normalizer` 类，核心是 `normalize(name)`：

- 输入去空白；空串原样返回。
- **链式别名解析**：`{"a":"b", "b":"c"}` 下 `normalize("a")` 返回 `"c"`，最多跳 10 次（`_MAX_HOP`）。
- **环保护**：`{"x":"y", "y":"x"}` 不会死循环，命中环即停止返回当前值。
- `normalize_all(names)`：批量归一化，去空、去重、保持首次出现顺序。

**设计要点**：归一化采用保守原则（标注规范第 9 节），只认别名字典里的明确等价，不自动推断。别名统一由数据模块在 `aliases.json` 维护。

#### 8. `cookkg/taxonomy.py` —— 食材层级（NetworkX 有向图）

`Taxonomy` 类在构造时把 `TaxonomyEdge` 装入 `nx.DiGraph`，边方向统一为 **`child → parent`**：

- `IS_A`：食材 → 类别（如 小米椒 → 辣椒）
- `SUBCLASS_OF`：子类别 → 父类别（如 辣椒 → 蔬菜）
- `HAS_COMPONENT`：复合食材 → 成分（如 豆瓣酱 → 辣椒）

**只加载 `review_state == "confirmed"` 的边**，未确认关系不参与推理。

关键查询方法（都基于一个私有 `_ancestors(node, relation)` 反向遍历）：

| 方法 | 语义 | 底层 |
| --- | --- | --- |
| `category_descendants(cat)` | 某类别的后代类别 | 沿 `SUBCLASS_OF` 反向 |
| `ingredients_of(cats)` | 这些类别下的食材 | 沿 `IS_A` 反向 |
| `containing_ingredients(comp)` | 含某成分的复合食材 | 沿 `HAS_COMPONENT` 反向 |
| `node_kind(name)` | 判定 ingredient/category/unknown | 查已登记节点集 |

**设计要点**：`_ancestors` 用显式栈做 BFS/DFS，而不是递归，避免深层级栈溢出；`node_kind` 优先返回 `category`（因为「辣椒」既是类别又可能是食材名，类别判定优先级更高，符合「上位类别排除」语义）。

#### 9. `cookkg/exclusion.py` —— 忌口推理（排除集合扩展）

这是「层级化忌口推理」创新点的实现。核心函数 `expand_exclusions(excludes, taxonomy, normalizer, use_component)`：

对每个排除项，先归一化，再按 `node_kind` 分三种情况处理：

1. **是类别**（如「辣椒」）：
   - 沿 `SUBCLASS_OF` 找后代类别；
   - 沿 `IS_A` 找这些类别下的所有食材（小米椒、朝天椒、青椒）；
   - **类别名本身加入字面兜底**——菜谱中若直接把「辣椒」当作食材名（如酸辣土豆丝的可选食材「辣椒」），同样命中；
   - 可选地沿 `HAS_COMPONENT` 找含这些成分的复合食材。
2. **是具体食材**（如「小米椒」）：直接排除该食材，可选沿 `HAS_COMPONENT` 找含它的复合食材。
3. **未知名称**：字面精确匹配兜底，不做层级推断。

返回 `ExclusionResult` 数据类，包含：
- `excluded_ingredients` / `excluded_categories` / `excluded_literals`：三份集合；
- `ingredient_paths`：食材 → 到排除项的图路径（供解释，如 `{"小米椒": ["小米椒", "辣椒"]}`）；
- `detail`：每个排除项扩展出的食材清单。

**关键设计决策**：

1. **成分扩展独立成 `_extend_components` 函数**，由 `use_component` 开关控制。默认关闭，仅在对照实验「层级 + 成分」方法中开启——对应 `PROJECT.md` 第 7.2 节「可选地查找经审核且来源明确的复合食材成分」，体现了渐进式范围控制。
2. **`ingredient_paths` 用 NetworkX `shortest_path`** 生成真实图路径，失败时退化为 `[节点, 目标]` 兜底，保证解释对象永远有路径可展示。
3. **`sorted_excluded()`** 合并三类集合并稳定排序，作为响应 `excluded_ingredients` 字段，保证输出可复现。

#### 10. `cookkg/filter.py` —— 候选硬约束过滤

实现 `FilteredRecipe` 数据类与 `filter_recipe` / `filter_recipes` 函数。这是「关系语义区分处理冲突」创新点的实现。

**`filter_recipe` 的处理顺序**：

1. **严格准入检查 `_check_admission`**：菜谱 `review_state != "confirmed"`、存在 `unknown` 需求语义、食材关系未确认、选择组定义缺失、`open_group=True`、`min_select > max_select` —— 任一不满足即淘汰。对应标注规范第 13 节「严格推荐准入条件」。

2. **选择组解析 `_resolve_groups`**：
   - `required_one_of`（必需组）：可用成员不足 `min_select` → 淘汰（如水煮鱼排除「蔬菜」命中全部垫底蔬菜）；否则**优先选库存/常备成员，其余按字典序**，保证可复现。
   - `optional_one_of`（可选组）：命中排除的成员直接省略，不产生补购（如蛋炒饭的熟肉备选组）。

3. **必需/可选食材逐条处理**：
   - `required` 命中排除 → **淘汰菜谱**（如小炒肉的必需小米椒命中「辣椒」），生成 `excluded` 解释；
   - `optional` 命中排除 → **保留并省略**（如酸辣土豆丝的可选辣椒），生成 `omitted` 解释，不进入补购。

4. **计算单菜补购与库存覆盖**：`buy = required - have - pantry`，`used_have = required & have`。

**设计要点**：命中判断用 `exclusion.all_excluded_ingredients()`（食材 ∪ 字面兜底），这样「辣椒」既是类别又被排除时，菜谱里作为可选食材的「辣椒」也能正确命中省略。

#### 11. `cookkg/recommend.py` —— 联合补购优化

实现 `recommend()` 函数与 `RecommendOutcome` 结果对象。这是「多菜联合补购优化」创新点的实现。

核心公式（`PROJECT.md` 第 7.4 节）：

```text
Buy(M) = Required(M) - Have - Pantry
```

流程：

1. `_rank_candidates`：单菜候选按 `(补购种类升序, 库存覆盖数降序, 稳定 ID)` 排序，**截取前 `candidate_cap`（默认 60）道**。
2. `itertools.combinations(pool, count)` 枚举所有 count 道菜组合。
3. 对每个组合：`required_union` 求并集（**共享缺料只计一次**），`buy = required_union - have - pantry`；超过 `max_buy` 的组合丢弃。
4. `_combo_plan` 构造方案：补购去重排序、库存覆盖排序、省略项按食材名去重（同一食材多道菜都省略时只列一次）。
5. 组合按 `(补购种类, 库存覆盖降序, 菜谱 ID 字典序)` 稳定排序，返回前 `limit` 个。

**`RecommendOutcome` 额外提供两个诊断字段**：
- `candidate_count`：进入枚举的候选数（响应里展示）；
- `min_buy`：所有组合中的最小补购种类（**不受 `max_buy` 限制**），用于无解时给出「最少需补购 N 种」的精确原因。

**诚实声明（重要）**：系统只承诺**候选池内最优**，不保证全局最优——这是 `PROJECT.md` 明确声明的范围（单菜候选截取前 60 道）。`count ≤ 3` 时若需全局最优，可把 `candidate_cap` 调大或改为全量枚举。

#### 12. `cookkg/engine.py` —— 推荐引擎（顶层编排）

`RecommendationEngine` 类把上述模块串成完整流水线，`recommend(request)` 方法执行五步：

1. **输入归一化**：have / pantry / exclude 三组统一 `normalize_all`。
2. **排除集合扩展**：调 `expand_exclusions`。
3. **候选过滤**：调 `filter_recipes`，得到候选与被淘汰列表。
4. **联合补购优化**：调 `recommend`。
5. **组装响应**，其中**无解原因分级**（`_no_candidate_reason`）：
   - 无候选时，区分「全部因忌口冲突被淘汰」和「数据未就绪（未审核/pending）」两类，给出不同措辞；
   - 有候选但无组合时，报告「候选 N 道菜中无法在 max_buy 内组合出 count 道菜（最少需补购 M 种）」。

**设计要点**：`_is_dietary_reject(reason)` 通过匹配「命中排除」「可用成员不足」关键词判断淘汰是否来自忌口约束，从而把「数据未就绪」与「用户忌口过严」区分开——这对应文档「无解时明确原因，不自动放宽条件」的要求。引擎从不修改用户输入，从不自动放宽条件。

#### 13. `cookkg/loader.py` —— 标准数据加载

- `DataBundle` 数据类打包 recipes / taxonomy / aliases。
- `_read_jsonl`：逐行读 JSONL，容忍空行，出错时带行号抛出 `DataLoadError`。
- `load_recipes` / `load_taxonomy`：JSON 行经 `Pydantic model_validate` 严格校验，不符合模型即抛错——**数据契约在加载时就强制校验**。
- `load_aliases`：别名字典，文件不存在返回空 dict（别名是可选的）。
- `load_all(data_dir)`：一站式加载三文件。

**设计要点**：算法模块对数据模块的依赖被收敛到这一个文件。数据模块（`Zouyilin06`）只要保证产出符合 `models.py` 契约的 JSONL，本模块就能直接消费。

#### 14. `cookkg/api.py` —— FastAPI 服务

`create_app(engine)` 工厂函数构建 FastAPI 应用，暴露两个端点：

| 端点 | 方法 | 作用 |
| --- | --- | --- |
| `/health` | GET | 健康检查，返回 `{"status": "ok", "recipes": N}` |
| `/recommend` | POST | 菜单推荐，`response_model=RecommendResponse` 自动生成 OpenAPI 文档与响应校验 |

**设计要点**：
- 用**工厂函数**而非模块级 `app`，便于测试注入不同引擎（`conftest` 里就注入样例引擎）。
- `response_model` 保证响应结构始终符合契约，前端拿到的一定是合法 `RecommendResponse`。

#### 15. `cookkg/cli.py` —— 命令行入口（Typer）

提供两个子命令：

| 命令 | 作用 |
| --- | --- |
| `recommend` | 离线执行一次推荐，支持 `--json` 输出，`candidate_cap` 可调 |
| `serve` | 启动 FastAPI 服务（`uvicorn.run`） |

`_split` 把逗号分隔的中文字符串拆成列表；`_render_text` 把响应渲染成人类可读的中文文本（含方案、补购、库存、省略项）。

#### 16. `data/recipes.jsonl` —— 9 道菜谱

每行一个 `Recipe`，覆盖了标注规范里所有关键场景：

| 菜谱 | 覆盖的场景 |
| --- | --- |
| 番茄炒蛋 | 必需食材（西红柿/鸡蛋/食用油/盐）+ 可选葱 |
| 酸辣土豆丝 | **可选辣椒**（命中排除应省略不淘汰） |
| 小炒肉 | **必需小米椒**（命中「辣椒」类别应淘汰，核心演示例） |
| 回锅肉 | **必需豆瓣酱**（含 `HAS_COMPONENT` 辣椒，成分推理例） |
| 蛋炒饭 | 可选黄瓜/胡萝卜 + **可选选择组**（灯影牛肉丝/午餐肉/腊肠） |
| 西红柿鸡蛋汤 | 可选味素 |
| 水煮鱼 | **必需选择组**（土豆/豆芽/花菜/生菜，垫底蔬菜） |
| 蒜蓉炒青菜 | 必需青菜/蒜 |
| 麻婆豆腐 | `review_state: "pending"`（**待审核，应被严格准入拒绝**） |

`source_hash` 字段我用了统一占位值，真实数据模块会填真实 SHA-256。

#### 17. `data/taxonomy.jsonl` —— 17 条层级边

覆盖三种关系：

- **`IS_A`**（食材→类别）：小米椒/朝天椒/青椒→辣椒；西红柿/土豆/豆芽/花菜/生菜/青菜/黄瓜/胡萝卜→蔬菜；鸡蛋→蛋类；五花肉→猪肉；豆瓣酱→酱料；蒜→香辛料。
- **`SUBCLASS_OF`**（类别→类别）：辣椒→蔬菜。
- **`HAS_COMPONENT`**（复合食材→成分）：豆瓣酱→辣椒。

这条「豆瓣酱→辣椒」的成分边是实验一「层级+成分」方法能拿到 recall=1.0 的关键。

#### 18. `data/aliases.json` —— 6 条别名

番茄/蕃茄→西红柿；马铃薯→土豆；蒜瓣/蒜末/大蒜→蒜。对应标注规范第 9 节「建议合并」的示例。

#### 20. `experiments/exp_exclusion.py` —— 实验一：忌口推理对照

比较四种方法的忌口冲突识别能力，指标为准确率/召回率/F1/误排除率：

| 方法 | 逻辑 | 实测 recall |
| --- | --- | --- |
| keyword | 食材名 == 排除项 的精确匹配 | 0.3333 |
| alias | 别名归一化后精确匹配 | 0.3333 |
| taxonomy | 层级图谱推理（本系统默认） | 0.6667 |
| component | 层级 + 成分推理 | **1.0** |

真值表 5 个样例（含小炒肉×辣椒、酸辣土豆丝×辣椒不淘汰、回锅肉×辣椒需成分推理等），用 TP/FP/TN/FN 四格统计。**结果证明层级推理比关键词匹配提高召回率且零误排除，成分推理进一步补齐召回**。

#### 21. `experiments/exp_purchase.py` —— 实验二：联合补购对照

比较三种选菜策略的补购种类数：

| 方法 | 实测 avg_buy | 实测 avg_cover |
| --- | --- | --- |
| random（随机选菜） | 3.5 | 3.0 |
| greedy（逐道选缺料最少） | 1.5667 | 3.2333 |
| joint（联合优化，本系统） | **1.5** | **3.6** |

**关键设计**：为保证公平，先 `_make_scenarios` 预生成 30 个固定库存场景，三种策略在**完全相同**的场景上评估；每个策略用独立随机源。结果证明联合优化比贪心补购更少、库存覆盖更高。

#### 22. `experiments/exp_semantics.py` —— 实验三：关系语义对照

比较「所有食材均视为必需」（all_required）与「区分必需/可选/选择组」（semantic）两种方法：

| 方法 | 可用候选 | 不必要补购项 |
| --- | --- | --- |
| all_required | 7 | 12 个 |
| semantic | 7 | **0 个** |

统计把可选食材、选择组成员都当成必需时多出来的「不必要补购」物品种类，证明语义区分能减少无效补购。

## 七、给答辩用的「我能讲什么」

作为算法与后端负责人，我可以就以下内容独立讲解：

1. **忌口推理**：排除「辣椒」如何沿 `SUBCLASS_OF` + `IS_A` 识别小米椒等，如何生成可解释的图路径；成分关系为什么默认关闭、何时开启。
2. **关系语义**：必需/可选/选择组三种冲突为何处理不同（淘汰 vs 省略 vs 按组判断），这是相对「全必需」方法的价值。
3. **联合补购**：`Buy(M) = Required(M) - Have - Pantry` 的并集去重，共享缺料只计一次；排序键如何保证可复现；候选池内最优的边界。
4. **API 与契约**：请求/响应模型如何与 UI、数据模块对齐，为什么字段变更要三人确认。
5. **三组实验**：每个实验的设计、公平性保证（固定场景/固定种子）、实测结果及其证明的结论。
